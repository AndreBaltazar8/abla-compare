# Zig HTTP comparison

This run adds a Zig implementation and rebuilds and reruns the entire workload
matrix. It is a fresh comparison, not a merge of Zig numbers with the previous
baseline.

## Zig implementation selection

The benchmark uses [Zig 0.16.0](https://ziglang.org/download/), the current
stable release, and pins
[`httpz` at `dce2cb0`](https://github.com/karlseguin/http.zig/tree/dce2cb07f1cd9beca6146869e1eec48025cf9f6f).
`httpz` is a pure-Zig HTTP/1.1 server with its own nonblocking event loop,
routing, middleware, request arenas, and explicit worker configuration. That
makes it a better language comparison than adapting a generic standard-library
server solely for this benchmark.

[Zap](https://github.com/zigzap/zap) was also investigated because its published
history makes it a credible high-throughput candidate, but it wraps the C
`facil.io` runtime. A same-core plaintext spot-check of the current Zap checkout
reached about 228,000 requests/second; `httpz` produced three samples between
334,082 and 335,344 requests/second before the full run. This spot-check was used
only to select the Zig implementation and is not part of the result table.

The final Zig server uses one `httpz` event-loop worker and two handler threads.
A same-core tuning pass found one handler thread at about 294,000 plaintext
requests/second, while 2, 4, 8, and the upstream default of 32 were clustered
around 334,000 to 338,000. Two was retained as the smallest configuration in
the top-performing group. The waiting coordinator makes four Zig OS threads in
total under load. All inherit the one-CPU server affinity, so they are scheduled
concurrently but cannot execute CPU work in parallel.

## Configuration

- Machine: Intel Core i9-13900K, Linux 6.17.3
- Server: one process pinned to CPU 6, a 5.8 GHz P-core
- Isolation: CPU 7, the SMT sibling of CPU 6, excluded from the client set
- Client: `oha` 1.10.0 pinned to CPUs 0-5 and 8-31
- HTTP/1.1 keep-alive, 64 connections
- 3 second warm-up, 3 x 5 second measured samples
- Toolchains: Zig 0.16.0, Go 1.25.1, Rust 1.95.0
- Builds: Zig `ReleaseFast`, stripped Go, Rust release with thin LTO, and the
  Abla production optimization pipeline
- Observed OS threads under plaintext load: Abla 1, Go 4, Rust 2, Zig 4; every
  server thread reported affinity to CPU 6

CPU 6/7 was selected after the earlier compiler workloads had finished and no
sustained high-CPU job remained on that core. This is affinity isolation from
the load generator, not kernel-level core isolation; light host daemons remained
running. Every release build command completed immediately before the run;
Cargo correctly reused its current unchanged Rust release artifact.

The resource being normalized here is one logical CPU, not one OS thread. Go,
Tokio, and `httpz` all maintain runtime or I/O threads, whereas the Abla server
is one event-loop thread. Because every server task is restricted to CPU 6,
none of those runtimes can obtain multi-core parallelism, but their thread and
I/O scheduling designs remain part of what this benchmark measures.

## Results

The table reports the median of three successful samples. `Zig vs` values are
throughput ratios, so values over 100% mean Zig was faster.

| Scenario | Abla req/s | Go req/s | Rust req/s | Zig req/s | Zig vs Abla | Zig vs Go | Zig vs Rust |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Plaintext | 265,698 | 167,827 | 279,849 | **326,243** | 122.8% | 194.4% | 116.6% |
| Parameters | 214,119 | 155,542 | 244,857 | **316,537** | 147.8% | 203.5% | 129.3% |
| Authenticated context | 209,826 | 159,154 | 250,003 | **331,717** | 158.1% | 208.4% | 132.7% |
| 16 KiB body | 156,345 | 102,344 | 156,788 | **160,183** | 102.5% | 156.5% | 102.2% |

| Scenario | Abla p50 | Go p50 | Rust p50 | Zig p50 | Abla p99 | Go p99 | Rust p99 | Zig p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Plaintext | 0.235 ms | 0.380 ms | 0.231 ms | **0.181 ms** | 0.458 ms | 0.799 ms | **0.245 ms** | 0.372 ms |
| Parameters | 0.294 ms | 0.410 ms | 0.263 ms | **0.187 ms** | 0.577 ms | 0.869 ms | **0.280 ms** | 0.372 ms |
| Authenticated context | 0.301 ms | 0.401 ms | 0.257 ms | **0.185 ms** | 0.578 ms | 0.854 ms | **0.272 ms** | 0.352 ms |
| 16 KiB body | 0.399 ms | 0.624 ms | 0.405 ms | **0.387 ms** | 0.798 ms | 1.288 ms | **0.450 ms** | 0.627 ms |

Zig/httpz is faster in all four throughput medians. Its largest lead is the
authenticated middleware and request-local workload, where it is 58.1% ahead
of Abla and 32.7% ahead of Rust. The 16 KiB echo is effectively a near tie:
Zig is 2.5% ahead of Abla and 2.2% ahead of Rust, moving about 2.44 GiB/s in
each direction on the server core.

Zig also has the best median p50 in every workload. Rust retains the best p99.
One Zig sample in each of the first three workloads had a roughly 1 ms p99
excursion; the other two samples were close to the reported 0.35-0.37 ms median.
Rust likewise had one lower-throughput 16 KiB sample (140,957 requests/second)
between two samples near 156,800. These variations are why the table uses
three-sample medians rather than the best sample.

All responses passed byte-for-byte validation before load, and all measured
samples had a 100% success rate. The full raw `oha` summaries and histograms are
retained locally in `build/2026-08-17-zig-all.json`.
