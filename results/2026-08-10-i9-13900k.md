# Baseline: 2026-08-10

Machine: Intel Core i9-13900K, Linux 6.17.3, one pinned server CPU, separate
client CPUs. The load was HTTP/1.1 keep-alive with 64 connections, a 3-second
warm-up, and three 10-second measurements. Values below are medians. Every
managed-memory measurement completed with HTTP 200 and the expected body.

| Server | Requests/second | p50 latency | p99 latency |
| --- | ---: | ---: | ---: |
| Abla Web + event HTTP | 4.7 | 12,922.026 ms | 13,691.603 ms |
| Go `net/http` | 163,968 | 0.389 ms | 0.816 ms |
| Rust Axum/Tokio | 281,578 | 0.229 ms | 0.244 ms |

Toolchains: Abla compiler at commit `3c7214d`, Go 1.25.1, Rust 1.95.0, Axum
0.8.9, Tokio 1.53.1, and oha 1.10.0.

## What the Abla result means

This is a real blocker, not evidence that routing alone costs 13 seconds. A
collector-free diagnostic initially serves about 4,400 requests/second, then
hits Abla's 1 GiB tracked-heap ceiling after about 13,800 successful requests
and aborts. Long-running Abla programs must select managed collection through
the memory API. With that correct configuration, automatic pressure collection
introduces repeated multi-second pauses and produces the sustained result in
the table.

The next optimization target is therefore allocation lifetime and collection
in the HTTP hot path: request-scoped regions or deterministic release for parsed
requests and rendered responses, fewer temporary strings/arrays, and pressure
safe points at request boundaries instead of deeply nested allocating function
entries. A router microbenchmark should be added separately to distinguish Web
dispatch cost from HTTP parsing, framing, socket I/O, and memory reclamation.
