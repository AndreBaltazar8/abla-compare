## Why processes, not shared-heap threads

The Abla event loop remains single-threaded within a worker. Each worker binds
the same address with Linux `SO_REUSEPORT`, so the kernel distributes accepted
connections while every process retains an independent allocator, tracing
collector, region-page cache, and failure boundary. Go and Tokio instead use
their existing multi-thread runtimes within one process.

Abla has native `thread` and `task` language constructs, but its hosted tracing
collector currently declines collection while another native thread is alive:
it cannot yet prove the other thread's complete root stack is stopped at a safe
point. Running permanent allocating HTTP loops as threads would therefore turn
the benchmark into an eventual memory-limit failure. The process-worker model
is the integrity-preserving parallel path until coordinated multi-thread root
scanning lands.

## Sustained parallel memory check

Four Abla workers completed a separate 60-second run at 256 connections with
100% success and 395,250 requests/second, approximately 23.7 million responses.
Peak RSS was 128,596-128,704 KiB per worker and 514,664 KiB in total. All four
workers remained alive and shut down cleanly after the run. This is the expected
cost of four independent managed heaps rather than a shared-heap memory result.

## Verification

The reusable-listener regression binds two live listeners to the same selected
port and requires both descriptors to remain valid. The complete 73-fixture
compiler/runtime/network suite passed, as did the byte-identical pure-Abla O2
self-rebuild. The parallel benchmark then completed all nine measured samples
with a 100% request success rate.
