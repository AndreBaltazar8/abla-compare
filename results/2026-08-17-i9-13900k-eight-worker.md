# Eight-worker HTTP comparison

This run compares the four implementations with up to eight simultaneously
active server workers on eight logical CPUs. Exact OS-thread totals are not a
portable resource boundary because Go, Tokio, and `httpz` retain runtime and
coordination tasks, so the controlled resources are active execution workers
and CPU affinity.

## Selected configurations

- Abla: 8 independent, single-threaded event-loop processes sharing the port
  with `SO_REUSEPORT`
- Go: one process with `GOMAXPROCS=8`
- Rust: one process with `TOKIO_WORKER_THREADS=8`
- Zig: one process with 2 `httpz` event-loop workers and 3 handler threads per
  event worker, for `2 x (1 + 3) = 8` active workers

Live inspection under load found 8 Abla processes/tasks, 14 Go runtime tasks,
9 Rust tasks, and 9 Zig tasks. Rust and Zig each include a waiting coordinator;
Go's additional runtime tasks remain subject to `GOMAXPROCS=8`. Every task in
all four servers had the same eight-CPU affinity, so none could execute on a
ninth logical CPU.

The selected server CPU set was `0,2,4,6,8,10,12,14`: one hardware thread from
each of the i9-13900K's eight P-cores. Their SMT siblings `1,3,5,7,9,11,13,15`
were kept out of the load generator. `oha` used the 16 E-cores, CPUs `16-31`.

Short tuning passes tested 2, 4, 6, and 8 execution workers. Abla, Go, and Rust
all selected 8. For Zig, the valid eight-active-worker layouts `1 x (1+7)`,
`2 x (1+3)`, and `4 x (1+1)` were tested on plaintext and the 16 KiB echo;
`2 x (1+3)` was the best balanced layout. Connection sweeps at 64, 128, and 256
showed additional throughput at 256, so the final run uses 256 connections.
That is a throughput-oriented saturation point and its roughly 4.1-4.3 ms p99
for the three fastest implementations is reported rather than hidden.

## Configuration

- Machine: Intel Core i9-13900K, Linux 6.17.3
- Protocol: HTTP/1.1 keep-alive
- Client concurrency: 256 connections
- Warm-up: 3 seconds per server and scenario
- Samples: 3 x 5 seconds per server and scenario
- Toolchains: Zig 0.16.0, Go 1.25.1, Rust 1.95.0
- Builds: Zig `ReleaseFast`, stripped Go, Rust release with thin LTO, and the
  Abla production optimization pipeline

All release build commands completed successfully. A remote Nix registry 429
on the first redundant rebuild attempt was avoided with the already-installed
registry snapshot; the rebuilt server hashes exactly matched the binaries used
for the measurements.

## Throughput

The table reports the median of three samples. Relative columns compare each
implementation with Abla in the same row.

| Scenario | Abla req/s | Go req/s | Rust req/s | Zig req/s | Go vs Abla | Rust vs Abla | Zig vs Abla |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Plaintext | **1,441,660** | 883,101 | 1,395,611 | 1,433,931 | 61.3% | 96.8% | 99.5% |
| Parameters | 1,352,675 | 787,079 | 1,324,724 | **1,419,430** | 58.2% | 97.9% | 104.9% |
| Authenticated context | **1,394,653** | 801,405 | 1,331,491 | 1,383,740 | 57.5% | 95.5% | 99.2% |
| 16 KiB body | **910,667** | 553,166 | 852,245 | 854,094 | 60.7% | 93.6% | 93.8% |

Abla and Zig are effectively tied on plaintext and authenticated context: the
median gaps are 0.5% and 0.8%, respectively. Zig leads the routed parameter
workload by 4.9%. Abla leads the 16 KiB echo by 6.6%; Zig and Rust are only 0.2%
apart there. Abla's body result moves about 13.90 GiB/s in each direction on
loopback, versus 13.03 GiB/s for Zig and 13.00 GiB/s for Rust.

## Latency

| Scenario | Abla p50 | Go p50 | Rust p50 | Zig p50 | Abla p99 | Go p99 | Rust p99 | Zig p99 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Plaintext | **0.105 ms** | 0.204 ms | 0.117 ms | 0.107 ms | 4.106 ms | **1.302 ms** | 4.115 ms | 4.108 ms |
| Parameters | 0.120 ms | 0.226 ms | 0.124 ms | **0.107 ms** | 4.114 ms | **1.635 ms** | 3.825 ms | 4.109 ms |
| Authenticated context | 0.119 ms | 0.222 ms | 0.125 ms | **0.113 ms** | 4.113 ms | **1.573 ms** | 4.091 ms | 4.113 ms |
| 16 KiB body | **0.169 ms** | 0.324 ms | 0.192 ms | 0.198 ms | 4.259 ms | **2.291 ms** | 4.278 ms | 4.224 ms |

Go has lower p99 values because it does not approach the throughput saturation
of the other three; its p50 is substantially higher in every workload. At this
connection count, the Abla, Rust, and Zig p99 values mostly reflect the common
saturated scheduling regime.

## Scaling from the one-CPU run

| Scenario | Abla gain | Go gain | Rust gain | Zig gain |
| --- | ---: | ---: | ---: | ---: |
| Plaintext | 5.43x | 5.26x | 4.99x | 4.40x |
| Parameters | 6.32x | 5.06x | 5.41x | 4.48x |
| Authenticated context | 6.65x | 5.04x | 5.33x | 4.17x |
| 16 KiB body | 5.83x | 5.41x | 5.44x | 5.33x |

These are observed throughput gains, not pure parallel-efficiency scores: the
one-CPU run used 64 connections and this saturation run uses 256. They still
show the main architectural result. Abla's independent event loops scale very
well, particularly for routing and context, while Zig's single-process `httpz`
small-response paths reach their throughput ceiling earlier. Zig scales better
on the large-body path than on the three small-response paths.

The Abla parameter samples ranged from 1.273M to 1.382M requests/second, and
several Go, Rust, and Zig workloads also had wider third-sample variation.
Consequently, gaps around 1% should be treated as ties rather than rank claims.
Every response passed byte-for-byte validation before load, and every measured
sample had a 100% success rate. Full raw `oha` summaries and histograms are
retained locally in `build/2026-08-17-8active-all.json`.
